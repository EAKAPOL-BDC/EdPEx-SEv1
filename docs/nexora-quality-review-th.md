# NEXORA: รายงานตรวจระบบและการปรับปรุง 7 ด้าน

วันที่จัดทำ 16 กันยายน 2569 · รุ่น Quality Upgrade

## ขอบเขตและข้อสรุป

ตรวจโค้ดและการทำงานในสภาพแวดล้อมทดสอบของระบบเดิม ตั้งแต่แบบฟอร์ม F01–F06 การคำนวณ การตรวจรับรอง Dashboard, Data Visualization และหลังบ้าน พร้อมเทียบรหัสตัวชี้วัดกับเอกสารที่แนบ ผลตรวจพบข้อบกพร่องที่แก้ได้ในโค้ด และความพร้อมใช้งานจริงที่ยังต้องตรวจบนระบบติดตั้งจริง ชุดนี้เป็นการปรับปรุงสะสม ไม่ใช่ใบรับรองความปลอดภัย ความถูกต้องของคำตอบที่ผู้ใช้กรอก หรือการผ่าน WCAG

เกณฑ์ EdPEx หมวด 4.2 ให้ความสำคัญกับคุณภาพข้อมูล ความพร้อมใช้งาน และความมั่นคงปลอดภัยของสารสนเทศ ใช้เป็นกรอบประเมินร่วมกับเอกสารตัวชี้วัดของหน่วยงาน อ้างอิง PDF เกณฑ์ฉบับ 2567–2570 หน้าไฟล์ 72–73 (เลขหน้าพิมพ์ 50–51)

## ผลตรวจและสิ่งที่แก้ไข

| ด้าน | ข้อค้นพบและผลกระทบ | การปรับปรุงในชุดนี้ | ข้อจำกัดที่ยังเหลือ |
|---|---|---|---|
| 1. Data Accuracy | หน้าผลจริงใช้การปัดเศษเริ่มต้น ขณะที่ผลสาธิต/เครื่องคำนวณใช้ HALF_UP ทำให้เลขกึ่งกลางแสดงต่างกันได้; ผลสาธิตที่บันทึกไว้ยังไม่ได้คำนวณย้อนกลับทุกครั้งที่แสดง | ใช้ ROUND_HALF_UP ให้ตรงกัน; ตรวจ hash ต้นทางและคำนวณผลสาธิตซ้ำก่อนนำไปแสดง; ตัดรายการที่ไม่ผ่านออก พร้อมแจ้งจำนวนและหยุด CSV ด้วย 409 | การตรวจย้อนกลับยืนยันความตรงกันของข้อมูลที่บันทึกกับสูตร ไม่ยืนยันข้อเท็จจริงภายนอกหรือความถูกต้องเชิงเนื้อหาทุกสูตร |
| 2. Data Completeness | รหัสในคลังตรงกับเอกสาร 63/63 แต่จำนวนรหัสไม่ใช่ความครบของผลจริงรายปี/กลุ่ม/มิติ; ยังไม่มีหน้าติดตามช่องว่างนี้ | เพิ่มเมนูคุณภาพข้อมูล เทียบรหัสพร้อมหน้า PDF อ้างอิง แยกยังไม่ผูกแบบฟอร์ม ยังไม่มีผลรับรอง มีผลแต่ยังไม่มีค่า ซ่อนค่า และตรวจไม่ผ่าน | ยังไม่มีตารางแผนข้อมูลที่คาดหวังครบทุกกลุ่ม/มิติ/บริบทของทุกปี จึงไม่รายงานว่า “ผลจริงครบ 100%” |
| 3. Data Consistency | เกณฑ์เปรียบเทียบเดิมใช้วันตัดข้อมูล ทำให้เวลาคนละชั่วโมงในวันเดียวกันอาจรวมกราฟได้ | ใช้เวลา cutoff แบบ UTC ที่ตรงกันจริงร่วมกับช่วงรายงาน รุ่นแบบฟอร์ม สูตร มิติ หน่วย และบริบท; แสดงเวลาในหน้ากราฟ; ชื่อรุ่นอ่านได้ | ข้อมูลคู่เทียบและแนวโน้มข้ามปีต้องมีนิยามความเทียบเคียงที่เจ้าของข้อมูลรับรองก่อน |
| 4. Critical Data Availability | ยังไม่มีจุดตรวจว่าบริการตอบหรือฐานข้อมูลเข้าถึงตารางหลักได้ และไม่มีตัวช่วยสำรองพร้อมหลักฐานตรวจไฟล์ | เพิ่ม /health/live/, /health/ready/; หน้าคุณภาพข้อมูลแสดงเวลาตรวจ ผลรับรองล่าสุด และรอบที่พ้นกำหนด; เพิ่มเครื่องมือ pg_dump ที่ไม่เขียนทับไฟล์ พร้อม SHA-256 manifest | ยังไม่ได้ตั้ง monitoring/scheduler/สำรองอัตโนมัติ และยังไม่ได้ซ้อมกู้คืนจริง; health readiness ไม่ใช่การตรวจข้อมูลทั้งฐาน |
| 5. Security | ขาด password validators และการจำกัดการลองเข้าสู่ระบบร่วมกันระหว่างหลาย process; การตั้งค่าผลิตจริงยังไม่บังคับแยกจากพัฒนา | เพิ่มนโยบายรหัสผ่านสำหรับการสร้าง/เปลี่ยนรหัสผ่าน, จำกัด login ผ่านฐานข้อมูลทั้ง portal/admin, CSRF ก่อนนับ, no-store/CSP และ headers; production profile ปฏิเสธ DEBUG=true, secret อ่อน และ wildcard hosts | บัญชีเดิมไม่ถูกบังคับเปลี่ยนรหัสผ่านทันที; ยังไม่มี MFA และยังไม่ใช่ผล penetration test; TLS/proxy/สิทธิ์ฐานข้อมูลต้องตรวจระบบติดตั้งจริง |
| 6. Usability Evaluation | ส่วนหัว/การ์ดบางส่วนใหญ่เกินไป เมนูยาว ข้อมูลผิดพลาดและงานที่ยังไม่บันทึกสังเกตยาก | จัดเมนูเป็นหมวด ลดความหนาแน่นของส่วนตกแต่ง เพิ่มเตือนออกจากหน้าเมื่อแก้ข้อมูล เพิ่ม error summary ที่เชื่อมไปช่องผิดพลาด รองรับ Escape/คีย์บอร์ด และตารางเลื่อนอ่านได้ | เป็นการประเมินเชิงหลักการและทดสอบพฤติกรรมโค้ด ยังไม่ได้ทดลองกับผู้ใช้จริงหรือให้คะแนน SUS |
| 7. Visual / UX/UI | หน้าต่าง ๆ ใช้ขนาด ระยะห่างและองค์ประกอบไม่สม่ำเสมอ | เพิ่ม design system ร่วมทั้ง portal, แบบสำรวจ และธีม admin: สี ตัวอักษร ระยะห่าง ปุ่ม ฟอร์ม ตาราง สถานะ โครงร่าง responsive; ปรับหลังบ้านให้กระชับและรองรับ TH/EN; รักษาโทนเฉพาะ Endlessloop/FineReport | เบราว์เซอร์ทดสอบเปิด localhost ถูกบล็อก ERR_BLOCKED_BY_CLIENT จึงยังไม่ยืนยันภาพบน Chrome/Windows มือถือ การขยาย 200% หรือ screen reader |

## วิธีอ่านหน้าคุณภาพข้อมูล

เมนูนี้อ่านผลจริงเฉพาะพื้นที่ที่ผู้ใช้มีสิทธิ์ `result.review` และ `calculation.validate` และเฉพาะช่วงรายงานที่เลือก ไม่รวมข้อมูลสาธิต เปิดหน้าและส่งออกได้โดยไม่เปลี่ยนคำตอบหรือสถานะรับรอง

- “รหัสในคลังเทียบเอกสาร 63/63” หมายถึงรหัสอ้างอิงครบเท่านั้น ไม่ได้หมายความว่ามีคำตอบหรือผลรับรองครบ
- “มีค่าผลรับรอง” หมายถึงมีค่าอย่างน้อยหนึ่งรายการของตัวชี้วัดนั้น ไม่ยืนยันครบทุกกลุ่ม มิติ หรือบริบท
- “ซ่อนค่า” หมายถึงมีผล แต่ข้อกำหนดการเปิดเผยไม่อนุญาตให้แสดง ไม่ใช่ศูนย์และไม่ถือเป็นข้อมูลหาย
- “ตรวจสอบไม่ผ่าน” มีลำดับความสำคัญเหนือสถานะมีค่าบางรายการ ต้องตรวจชุดผลต้นทางก่อนใช้ข้อมูล
- ตัวเลขในตารางเป็นจำนวนรายการผลตามกลุ่ม/มิติ ไม่ใช่จำนวนผู้ตอบ CSV ไม่มีคำตอบรายบุคคลหรือค่าที่ถูกซ่อน
- รายการ 63 รหัสมาจากไฟล์สรุปตัวชี้วัด 13 หน้า มี SHA-256 และเลขหน้าใน `catalog/indicator_reference.json` เพื่อระบุเอกสารอ้างอิงที่ใช้

## ข้อกำหนดที่ยังไม่ชัดเจน

เอกสารสรุปตัวชี้วัดหน้า 1 ระบุกลุ่ม **C3.2 สำหรับ 7.4-8** แต่ข้อความที่กล่าวถึงตัวชี้วัดเดียวกันในหน้าอื่นไม่ได้ระบุกลุ่มนี้ ชุดนี้บันทึกเป็นข้อสังเกตในหน้าคุณภาพข้อมูล ยังไม่เพิ่มกลุ่ม คำถาม หรือตัวหารโดยเดา ต้องให้เจ้าของตัวชี้วัดระบุนิยามที่ใช้เป็นทางการก่อนแก้คลังและออกรุ่นแบบฟอร์ม

## การออกแบบและความปลอดภัยที่เลือกใช้

ปุ่มทำงานหลักกำหนดพื้นที่กดอย่างน้อย 44 พิกเซล ตัวเลือกแบบประเมิน 48 พิกเซล ตัวอักษรช่องกรอก 16 พิกเซล มี focus ชัดและข้อความกำกับสถานะ สีไม่ใช่ช่องทางเดียวที่ใช้สื่อความหมาย ตารางยังคงโครงสร้างตารางและเลื่อนด้วยแป้นพิมพ์ได้ ส่วน sticky action ถูกปรับไม่ให้บังเนื้อหา ใช้แนวทาง [W3C เรื่องขนาดเป้าหมาย](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) และ [สิ่งเพิ่มเติมใน WCAG 2.2](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/) เป็นแนวทางออกแบบ ยังไม่ได้รับรองการผ่านมาตรฐาน

นโยบายรหัสผ่านกำหนดอย่างน้อย 15 ตัวอักษร และตรวจรหัสที่พบบ่อย ตัวเลขล้วน และความคล้ายกับข้อมูลผู้ใช้ จำกัดคำขอเข้าสู่ระบบ 12 ครั้งต่อชื่อบัญชี และ 300 ครั้งต่อที่อยู่เครือข่ายที่เซิร์ฟเวอร์เห็น ภายใน 10 นาที นับทุกความพยายาม ไม่ได้เก็บ username/IP แบบอ่านตรงได้ในตารางตัวนับ ไม่ใช้ X-Forwarded-For ที่ผู้ส่งอาจปลอม การใช้งานผ่านเครือข่ายมหาวิทยาลัยหรือ proxy ต้องทดสอบภาระจริงและวาง rate limit ที่ขอบเครือข่ายเพิ่มเติม แนวทางอ้างอิง [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

ค่าตั้ง production บังคับ HTTPS/cookie flags, SECRET_KEY ที่เหมาะสม, DEBUG=false และ hosts ที่ระบุชัด พร้อมกำหนด STATIC_ROOT เพื่อเตรียม collectstatic ส่วนการวาง WSGI server, reverse proxy, certificate และระบบสำรองยังเป็นงานติดตั้งจริงตาม [Django Deployment Checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/) ตัวเปิดเว็บ Windows ที่แนบเป็นตัวเปิดทดสอบบน loopback ตามเดิม

## ผลการตรวจสอบ

ผลทดสอบพร้อมจำนวนและคำสั่งอยู่ใน `TEST-RESULTS.txt` ของชุดติดตั้ง การทดสอบใช้ฐานข้อมูลแยกชั่วคราว ไม่ได้แก้ฐานข้อมูลของผู้ใช้ ครอบคลุมสูตรตัวอย่างอ้างอิง, การตรวจ input, ความสอดคล้องของเวลา/การปัดเศษ, demo replay, สิทธิ์ข้ามพื้นที่, ข้อมูลกลุ่มเล็ก, การรับรอง/แทนที่ผล, การจัดการแบบฟอร์ม/บัญชี, แบบประเมิน F01–F06 และ 17 กลุ่ม, login/CSRF, production configuration, health probe, เครื่องมือสำรองแบบจำลอง และพฤติกรรม JavaScript

การทดสอบเครื่องมือสำรองจำลองการเรียก pg_dump เพื่อตรวจ checksum การไม่เผยรหัสผ่านใน command line และการไม่ลบไฟล์ของงานอื่น ไม่ใช่หลักฐานว่าฐานข้อมูลจริงสำรองหรือกู้คืนสำเร็จ

## งานถัดไปเรียงตามความจำเป็น

| ลำดับ | งาน | หลักฐานที่ควรได้ |
|---|---|---|
| ก่อนเปิดใช้งานจริง | ตรวจรับหน้าจอบนเครื่องผู้ใช้และอุปกรณ์จริง ตั้งค่า HTTPS/production และสิทธิ์; ซ้อม backup–restore ในฐานแยก | ภาพและผล UAT, configuration review, log การกู้คืนและเวลาใช้งานกลับ |
| ก่อนใช้สรุปรายงานทางการ | ยืนยัน C3.2 ของ 7.4-8 และนิยามตัวชี้วัด รวมรายการผลที่คาดหวังรายช่วง/กลุ่ม/มิติ/บริบท | ตาราง data dictionary/coverage ที่ผู้รับผิดชอบรับรอง ไม่ใช้จำนวนรหัสแทนความครบของผล |
| ความต่อเนื่องบริการ | กำหนดผู้รับผิดชอบ RPO/RTO, scheduler, retention, monitoring/alert และ MFA สำหรับผู้ดูแล | ผลทดสอบเงื่อนไขล้มเหลว การแจ้งเตือน และการกู้คืนตามเวลาที่ตกลง |
| การใช้งานข้อมูลระยะยาว | นำเข้าประวัติพร้อมตรวจรับ แนบหลักฐาน เป้าหมาย คู่เทียบและแนวโน้มข้ามปี | ข้อมูลต้นทางและประวัติอนุมัติที่ตรวจย้อนกลับได้ |

UAT ที่เสนอ: ให้ผู้ตอบหลายช่วงวัยทำงาน “เปิดแบบประเมิน → ตอบ → แก้ข้อผิดพลาด → บันทึกฉบับร่าง → ส่ง” และให้ผู้ดูแลทำ “สร้างรอบ → คำนวณ → รับรอง → ตรวจคุณภาพ → อ่านกราฟ/ส่งออก” บันทึกอัตราสำเร็จ เวลาทำงาน จุดผิดพลาด และข้อเสนอแนะ ทดสอบหน้าจอ 390/768/1366 พิกเซล การขยาย 200% แป้นพิมพ์และ screen reader ก่อนให้คะแนน usability อย่างเป็นทางการ
