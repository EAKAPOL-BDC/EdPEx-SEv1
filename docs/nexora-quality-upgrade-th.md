# คู่มือ NEXORA Quality Upgrade

ชุดสะสมนี้รวม Data Visualization แบบ Endlessloop/FineReport, หน้าทำแบบประเมิน, ดูแบบประเมินตามกลุ่ม, F05, หลังบ้าน และการแก้ไขรุ่นก่อน พร้อมหน้า **คุณภาพข้อมูล** และการปรับปรุง 7 ด้าน ไม่มี migration ใหม่ในรุ่นนี้

## ติดตั้งสำหรับเครื่อง Windows เดิม

1. ดาวน์โหลด `nexora-quality-upgrade.zip` แล้วแตกลง `Downloads\nexora-quality-upgrade` ให้เห็น `nexora_web_update.py` ในโฟลเดอร์นั้น
2. หยุดเว็บเดิมด้วย Ctrl+C และรันใน PowerShell เดิมที่ใช้เปิดระบบ:

```powershell
& "$env:USERPROFILE\EdPEx-Web\EdPEx-SEv1\.venv\Scripts\python.exe" "$env:USERPROFILE\Downloads\nexora-quality-upgrade\nexora_web_update.py" --apply-schema
```

3. ใช้บัญชีและรหัสผ่านเดิม เปิด URL ที่ตัวติดตั้งแสดง แล้วกด Ctrl+F5
4. เปิด **คุณภาพข้อมูล** เลือกช่วงรายงาน และตรวจสถานะรายตัวชี้วัด ผู้ใช้ต้องมีสิทธิ์ดู/ตรวจผลในพื้นที่นั้น

ตัวติดตั้งสร้าง checkout แยกใน `EdPEx-Previews` ไม่ทับงานโค้ดเดิม ไม่ seed หรือแก้บัญชีจากการติดตั้ง รุ่นนี้ไม่มีการเปลี่ยน schema เพิ่มจากรุ่นก่อน แต่ `--apply-schema` ใช้ตรวจ/ติดตั้งเฉพาะ migration ในแผนรุ่นที่เคยมีอยู่ หากรันจากรุ่นเก่ากว่า ไม่เปลี่ยนฐานข้อมูลเพราะเปิด Dashboard

หากต้องกลับรุ่นก่อน ให้หยุดตัวเปิดรุ่นนี้แล้วเรียกตัวเปิดจากชุดก่อนหน้า โค้ดเดิมยังอยู่ สำหรับการย้อน schema ให้ยึด SCHEMA-UPDATE.md; ไม่สั่ง reverse migration โดยอัตโนมัติ

## ตรวจรับหลังติดตั้ง

- หน้าหลัก เมนูและหลังบ้านจัดวางถูกต้องทั้งจอกว้างและมือถือ ไม่มีปุ่มบังช่องกรอก
- แบบประเมินยังเปลี่ยนหมวด บันทึกฉบับร่างและส่งได้ ข้อที่ผิดมีข้อความ และออกจากหน้าที่แก้ไขแต่ยังไม่บันทึกมีคำเตือนของเบราว์เซอร์
- ดูแบบประเมินเปิด F01–F06 ตามกลุ่มได้โดยไม่สร้างคำตอบจริง
- คุณภาพข้อมูลแยก “ยังไม่มีผล” กับ “มีผลแต่ซ่อนค่า” และค่าศูนย์ยังคงเป็นศูนย์
- Endlessloop/FineReport เลือกข้อมูลจริงหรือข้อมูลสาธิตได้ หน่วยตรงกัน และ CSV ตรงตัวกรอง
- สร้าง/เปลี่ยนรหัสผ่านใช้ข้อกำหนดใหม่อย่างน้อย 15 ตัวอักษร บัญชีเดิมยังเข้าสู่ระบบด้วยรหัสเดิมได้

เบราว์เซอร์ในสภาพแวดล้อมพัฒนาเปิด localhost ถูกบล็อก จึงยังไม่ได้ตรวจภาพบน Chrome/Windows ของผู้ใช้ การทดสอบเซิร์ฟเวอร์และ JavaScript ไม่แทนการตรวจรับหน้าจอจริง

## ข้อมูลสาธิต

ข้อมูลที่มีอยู่ใช้ได้ต่อ หากต้องสร้างข้อมูลสาธิต ให้หยุดเว็บและเรียก `setup_demo_dashboard.py --apply` ด้วย Python เดิม ตัวช่วยใน ZIP เป็นชุดเดิมที่แยกข้อมูลสาธิตจากคำตอบจริง รันซ้ำไม่เพิ่มรายการซ้ำ ชุดนี้ไม่ได้สร้างข้อมูลบนเครื่องผู้ใช้โดยอัตโนมัติ

## จุดตรวจความพร้อม

- `/health/live/`: บริการตอบคำขอได้
- `/health/ready/`: ต่อฐานข้อมูลและอ่านโครงสร้างตารางพื้นที่/การคำนวณหลักได้ ตอบ 200 เมื่อผ่าน และ 503 เมื่อไม่พร้อม ไม่แสดงชื่อโฮสต์ รหัสผ่าน หรือข้อความฐานข้อมูล

ทั้งสองจุดเป็น GET/HEAD และไม่แทนการตรวจความครบของข้อมูลหรือการทดสอบกู้คืน หน้าเว็บคุณภาพข้อมูลจะแสดงวันเวลาที่ตรวจและสถานะผลจริงเพิ่มเติม ยังไม่ได้เชื่อมระบบแจ้งเตือนอัตโนมัติ

## สำรองฐานข้อมูลด้วยเครื่องมือใหม่

อยู่ที่ `scripts/backup_database.py` ใน checkout ที่ติดตั้งใหม่ ต้องมี PostgreSQL client (`pg_dump`) ใน PATH และตั้ง environment การเชื่อมต่อเดียวกับระบบไว้ใน process ที่รันสคริปต์ ตัวเปิดเว็บอาจรับรหัสผ่านเฉพาะ child process จึงอย่าคิดว่าสคริปต์สำรองจะได้รับค่านั้นโดยอัตโนมัติ สคริปต์ไม่มีหน้ารับรหัสผ่านและไม่เลือกฐานข้อมูลให้อย่างเงียบ ๆ

ตัวอย่างเมื่ออยู่ในโฟลเดอร์ checkout ที่ถูกต้อง และตั้งค่าฐานข้อมูลเรียบร้อยแล้ว:

```powershell
& "$env:USERPROFILE\EdPEx-Web\EdPEx-SEv1\.venv\Scripts\python.exe" .\scripts\backup_database.py --output "D:\NEXORA-Backups\nexora-before-update.dump"
```

ต้องสร้างโฟลเดอร์ปลายทางที่จำกัดสิทธิ์ไว้ก่อน และเลือกชื่อไฟล์ใหม่ จะได้ `.dump` และ `.dump.json` ซึ่งมี SHA-256 ขนาดไฟล์ และเวลาสร้าง ไม่เขียนทับไฟล์เดิม ไม่ restore หรือลบข้อมูลฐานข้อมูล ควรใช้ pg_dump รุ่นที่รองรับเซิร์ฟเวอร์นั้น และจัดการสิทธิ์โฟลเดอร์/การเข้ารหัส/การเก็บรักษาตามระบบจริง โดยเฉพาะ Windows ACL

manifest ระบุ `restore_tested: false` เสมอในขั้นสร้าง ต้องนำไปทดสอบกู้คืนในฐานข้อมูลแยกและบันทึกผลต่างหาก จึงจะใช้ยืนยันความสามารถกู้คืนได้ ยังไม่มี scheduler ในชุดนี้

## สำหรับผู้ดูแลที่เตรียมระบบใช้งานจริง

ตัวเปิด Windows ใช้ Django development server บน `127.0.0.1` เพื่อทดสอบตามเดิม ไม่ใช่ production deployment

โค้ดรองรับ `NEXORA_ENVIRONMENT=production` โดยต้องตั้ง `DJANGO_DEBUG=false`, `DJANGO_ALLOWED_HOSTS` เป็นรายชื่อจริงที่ชัดเจน และ `DJANGO_SECRET_KEY` ที่สุ่มและเก็บเป็นความลับอย่างน้อย 50 ตัวอักษร ระบบจะไม่เริ่มหากตั้งค่าเหล่านี้ไม่ผ่าน ไม่ควรเปิด profile นี้ผ่านตัวเปิด local ที่กำหนด DEBUG=true

สำหรับ deployment จริง ให้ใช้ WSGI server, HTTPS, staticfiles หลัง collectstatic, credentials ของฐานที่ถูกต้อง และตรวจด้วย `manage.py check --deploy` หากอยู่หลัง proxy ตั้ง `NEXORA_TRUST_HTTPS_PROXY=true` ได้เฉพาะเมื่อ proxy ล้าง header ที่ผู้ใช้ส่งมาและตั้งค่าเองอย่างเชื่อถือได้ ต้องตรวจ cookie/redirect ด้วย URL จริง

รักษา SECRET_KEY เดิมระหว่างอัปเดตตามปกติ การย้ายจาก secret สำหรับพัฒนาไป production ต้องวางแผนออก session/รหัสเข้าถึงใหม่ตามการใช้ HMAC ของระบบ ไม่สุ่มเปลี่ยน key ทุกครั้งที่เริ่มเว็บ

รายงาน `QUALITY-REVIEW-TH.md` อธิบายข้อค้นพบและงานที่ยังต้องพัฒนา ส่วน `TEST-RESULTS.txt` ระบุผลทดสอบจริงในชุดนี้
