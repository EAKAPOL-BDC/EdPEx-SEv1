# Release preparation — 21 September 2026

This is a release candidate, not confirmation that a production website is live.
The GitHub repository is public. Database archives, application secrets, respondent
data and local exports must never be committed or attached to a public pull request.

## Runtime

The Dockerfile installs pinned production dependencies, builds versioned static
assets with WhiteNoise, and runs Gunicorn as an unprivileged user. The image build
does not require production credentials. Startup does not migrate, seed, reset,
publish rounds or import data. HTTP request access logging is deliberately omitted
because invitation and proof URLs can contain confidential tokens.

Configure these values through the selected host's secret/environment settings:

- `DJANGO_SETTINGS_MODULE=edpex.production`
- `NEXORA_ENVIRONMENT=production`, `DJANGO_DEBUG=false`
- `DJANGO_SECRET_KEY`: independently generated private value, at least 50 characters
- `DJANGO_ALLOWED_HOSTS`: exact production hostname, without a scheme or wildcard
- `NEXORA_PUBLIC_ORIGIN`: matching HTTPS origin
- `DJANGO_DATABASE_PROFILE=supabase`
- `SUPABASE_DEV_DB_HOST`, `SUPABASE_DEV_DB_PORT`, `SUPABASE_DEV_DB_NAME`,
  `SUPABASE_DEV_DB_USER`, `SUPABASE_DEV_DB_PASSWORD`: selected Supabase PostgreSQL
  session connection values (the existing variable names are retained for compatibility)
- `NEXORA_TRUST_HTTPS_PROXY=true` only when the host strips untrusted forwarded headers

The feature flags remain disabled by default. Do not enable live participation
merely to remove a TEST label. Existing proof realms and data classifications must
be preserved. The current public setup workflows create synthetic rounds; a
separately validated real-data creation path is still required before live intake.

## Data and launch gates

Supabase Data API roles are separate from Django user accounts. Apply
`scripts/harden_supabase_data_api.sql` as the migration owner before real data is
imported and verify that `anon`/`authenticated` cannot access the Django tables.
The script preserves the PostgreSQL owner's access and business records; it revokes
Data API privileges only on tables/sequences with this application's prefixes and
removes automatic public grants for future tables created by `postgres`.

The selected target project is `edpex-development`. It contains a pre-existing
Django database. Do not restore a local dump over that database or use reset,
truncate, clean, or flush operations. Existing records must first be backed up and
compared with the source. Any necessary deletion or replacement requires the
owner's explicit approval for the exact records. Tests run on disposable local
PostgreSQL databases only, never on the Supabase target.

Before cutover: identify the Django host and HTTPS URL; verify a fresh source backup
by restoring it into a new isolated database; preserve the target; review schema
migrations and record conflicts; rehearse import and compare counts/fingerprints;
validate production configuration and static assets; then smoke-test authentication,
permissions, F01–F06, conditional questions, submission and proof verification using
explicit test fixtures. Do not expose test fixtures as real survey results.

`/health/live/` checks the process. `/health/ready/` checks basic database connectivity;
it is not a substitute for the release migration and application smoke tests.
